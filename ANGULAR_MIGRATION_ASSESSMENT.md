## 📋 Детальный анализ по категориям

### 1. Архитектура и структура кода

#### ✅ Положительные факторы
- **Clean Architecture** - четкое разделение слоев (Domain, Application, Infrastructure, Interface Adapters)
- **Модульная структура** - каждый модуль изолирован
- **Dependency Injection** - уже используется Inversify (можно адаптировать под Angular DI)
- **TypeScript** - полная типизация, что упростит миграцию
- **Порты и адаптеры** - паттерн хорошо совместим с Angular

#### ⚠️ Проблемные области
- **React-специфичные паттерны**: ~250+ использований React hooks (useState, useEffect, useCallback, useMemo)
- **Next.js App Router**: использование специфичных возможностей (layout.tsx, page.tsx, route.ts)
- **Client Components**: директивы 'use client' требуют переработки
- **Server Components**: Next.js Server Components не имеют прямого аналога в Angular

**Оценка сложности**: 7/10

---

### 2. UI компоненты и представления

#### Текущее состояние
- **155 TSX файлов** - все React компоненты
- Использование **JSX синтаксиса**
- **React hooks** для управления состоянием
- **Tailwind CSS** - можно сохранить

#### Что нужно изменить
- ✅ **JSX → Angular Templates** - полная переработка синтаксиса
- ✅ **React Hooks → Angular Services/Components** - другой подход к управлению состоянием
- ✅ **Props → @Input/@Output** - изменение системы передачи данных
- ✅ **useEffect → ngOnInit/ngOnDestroy** - другой lifecycle
- ⚠️ **MobX** (в web-shop-client) → Angular Services + RxJS

**Оценка сложности**: 9/10

---

### 3. Роутинг и навигация

#### Next.js App Router особенности
- Файловая система роутинга (`app/[pageSlug]/page.tsx`)
- Динамические роуты через `[param]`
- Server-side routing через `route.ts`
- `useRouter`, `usePathname`, `useSearchParams` hooks

#### Миграция на Angular Router
- ✅ **Файловая система → Angular Router** - потребуется ручная настройка routes
- ✅ **Server Routes → Angular Guards/Resolvers** - другой подход
- ✅ **Hooks → Router service** - изменение API

**Оценка сложности**: 6/10

---

### 4. API Routes и Server-side логика

#### Текущая реализация
- **~30 API routes** в формате Next.js (`app/api/*/route.ts`)
- Server-side обработка запросов
- Интеграция с Supabase, Stripe

#### Варианты миграции

**Вариант A: Angular + NestJS (рекомендуется)**
- Angular для фронтенда
- NestJS для API (совместим с текущей архитектурой)
- Сохраняется Clean Architecture
- ✅ Можно переиспользовать большую часть бизнес-логики

**Вариант B: Angular + Express/Fastify**
- Angular для фронтенда
- Express/Fastify для API
- Требует больше переработки

**Вариант C: Angular Universal (SSR)**
- Полностью Angular решение
- SSR через Angular Universal
- ⚠️ Ограниченные возможности по сравнению с Next.js

**Оценка сложности**: 7/10 (с NestJS), 8/10 (без NestJS)

---

### 5. State Management

#### Текущее состояние
- **web-shop-client**: MobX 6.15.0 + mobx-react-lite
- **web-shop**: React hooks (useState, useEffect)
- **EventBus** для межмодульного общения (Inversify)

#### Миграция на Angular
- ✅ **MobX → Angular Services + RxJS** - потребуется переработка
- ✅ **EventBus** - можно сохранить или заменить на RxJS Subject/BehaviorSubject
- ✅ **React hooks → Angular Services** - другой паттерн

**Оценка сложности**: 8/10

---

### 6. Dependency Injection

#### Текущая реализация
- **Inversify** с декораторами `@injectable()`, `@inject()`
- Модульная структура с bind функциями
- Типизированные TYPES символы

#### Миграция на Angular DI
- ✅ **Inversify → Angular DI** - похожий подход, но другой синтаксис
- ✅ **Декораторы** - Angular использует свои декораторы
- ✅ **Модули** - Angular Modules vs текущая модульная структура

**Оценка сложности**: 6/10

---

### 7. Тестирование

#### Текущее состояние
- **Vitest** для unit/integration тестов
- **Playwright** для E2E тестов
- **Testing Library** для React компонентов

#### Миграция на Angular тестирование
- ✅ **Vitest → Jasmine/Karma или Jest** - потребуется переписать тесты
- ✅ **Testing Library → Angular Testing Utilities** - другой API
- ✅ **Playwright** - можно сохранить для E2E

**Оценка сложности**: 7/10

---

### 8. Стилизация

#### Текущее состояние
- **Tailwind CSS** 3.4.18
- CSS модули в некоторых местах
- Inline styles через style prop

#### Миграция
- ✅ **Tailwind CSS** - полностью совместим с Angular
- ✅ **CSS модули** - Angular поддерживает
- ⚠️ **Inline styles** - нужно адаптировать под Angular синтаксис

**Оценка сложности**: 3/10

### Оценка времени для разных размеров команды

#### Коэффициент распараллеливания задач

Не все задачи можно распараллелить идеально из-за зависимостей между модулями. Реальный коэффициент эффективности:

| Размер команды | Коэффициент эффективности | Реальная оценка |
|----------------|---------------------------|-----------------|
| **1 разработчик** | 100% | **14-19 недель** |
| **2 разработчика** | 80% (некоторые зависимости) | **9-12 недель** |
| **3 разработчика** | 70% (больше координации) | **7-9 недель** |
| **4 разработчика** | 60% (много координации) | **5-7 недель** |
| **5+ разработчиков** | 50% (overhead координации) | **4-6 недель** |

**Формула:** `Время = (14-19 недель) / (Количество разработчиков × Коэффициент эффективности)`

## 🤖 Оценка времени с использованием ИИ

### Сценарий: ИИ-ассистированная миграция

ИИ может значительно ускорить миграцию, но требует человеческого контроля и валидации.

### Эффективность ИИ по типам задач

| Тип задачи | Эффективность ИИ | Ускорение | Требует контроля |
|------------|------------------|-----------|-----------------|
| **Domain слой** | 95% | 10-15x | Минимальный (только проверка) |
| **Application слой** | 85% | 8-12x | Средний (проверка DI) |
| **Infrastructure слой** | 70% | 5-8x | Высокий (проверка HTTP клиента) |
| **Presenters** | 75% | 6-10x | Средний (проверка RxJS) |
| **UI компоненты (TSX → Angular)** | 60% | 3-5x | **Очень высокий** (проверка логики) |
| **Тесты** | 80% | 6-10x | Высокий (валидация покрытия) |
| **Интеграция** | 40% | 2-3x | **Критический** (только человек) |

---

### Сценарии использования ИИ

#### Сценарий 1: **ИИ как основной инструмент + 1 разработчик (контроль)**

**Распределение работы:**
- **ИИ**: Генерация кода (80-90% работы)
- **Разработчик**: Code review, валидация, интеграция, тестирование

**Время**: **3-5 недель** (вместо 14-19 недель)

**Процесс:**
1. **Неделя 1**: ИИ мигрирует Domain + Application слои (автоматически)
2. **Неделя 2**: ИИ мигрирует Infrastructure слой (с проверкой)
3. **Неделя 3**: ИИ мигрирует UI компоненты (требует много правок)
4. **Неделя 4**: Разработчик интегрирует, исправляет ошибки
5. **Неделя 5**: Тестирование и финальная полировка

**Преимущества:**
- ✅ Быстрое генерирование кода
- ✅ Консистентный стиль
- ✅ Меньше человеческих ошибок в рутинных задачах

**Недостатки:**
- ⚠️ Требует тщательного code review
- ⚠️ ИИ может пропустить edge cases
- ⚠️ Интеграция требует человеческого контроля

---

#### Сценарий 2: **ИИ + 2 разработчика (оптимально)**

**Распределение работы:**
- **ИИ**: Генерация кода, рефакторинг
- **Dev 1**: Code review Domain/Application, архитектурные решения
- **Dev 2**: Code review Infrastructure/UI, интеграция, тестирование

**Время**: **2-3 недели** (вместо 9-12 недель)

**Процесс:**
1. **Неделя 1**: 
   - ИИ мигрирует Domain + Application (параллельно)
   - Dev 1: Code review и валидация
   - Dev 2: Настройка инфраструктуры Angular + NestJS

2. **Неделя 2**:
   - ИИ мигрирует Infrastructure + UI компоненты
   - Dev 1: Code review Infrastructure
   - Dev 2: Code review UI, исправление ошибок

3. **Неделя 3**:
   - Интеграция всех модулей
   - Тестирование
   - Финальная полировка

**Преимущества:**
- ✅ Максимальная скорость
- ✅ Хорошее качество (двойной контроль)
- ✅ Параллельная работа

---

#### Сценарий 3: **ИИ как помощник (консервативный подход)**

**Распределение работы:**
- **ИИ**: Только рутинные задачи (Domain, простые Use Cases)
- **Разработчики**: Вся остальная работа

**Время**: **6-8 недель** (вместо 14-19 недель)

**Преимущества:**
- ✅ Высокое качество (человеческий контроль)
- ✅ Меньше рисков
- ✅ ИИ ускоряет только безопасные части

## 🏗️ Влияние Clean Architecture на миграцию

Если бы проекты не использовали Clean Architecture, миграция была бы значительно сложнее.

---

### Сравнение: С Clean Architecture vs БЕЗ Clean Architecture

| Аспект | С Clean Architecture | БЕЗ Clean Architecture | Разница |
|--------|---------------------|------------------------|---------|
| **Процент переиспользования кода** | **~68%** | **~20-30%** | **-40-50%** |

  constructor(
    private readonly queryService: ProductQueryServicePort
  ) {}

**БЕЗ Clean Architecture:**
```typescript
// Бизнес-логика в компоненте
export function ProductsPage() {
  const [products, setProducts] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);
  
  useEffect(() => {
    const loadProducts = async () => {
      setLoading(true);
      try {
        // Нужно извлечь эту логику
        const response = await fetch(`/api/products?appId=${appId}`);
        if (!response.ok) throw new Error('Failed to load');
        const data = await response.json();
        
        // Валидация - нужно извлечь
        const validated = data.products.map(p => {
          if (!p.title) throw new Error('Invalid product');
          return p;
        });
        
        setProducts(validated);
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    };
    loadProducts();
  }, [appId]);
  
  // UI код
  return <div>{/* ... */}</div>;
}
```

1. Извлечь логику загрузки в отдельный класс/функцию
